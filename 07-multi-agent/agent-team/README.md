# agent-team — эталон финальной практики урока 7.4

Три задания практики модуля 7 в одном пакете. Сначала попробуйте сами — потом
сверяйтесь. Всё гоняется в обычном окружении курса (`ml_env`); оффлайн-тесты
не требуют Ollama.

| Задание | Что здесь | Живьём |
|---|---|---|
| 1. Полный автомат на LangGraph | `team/graph.py` + эталон `team/imperative.py` (7.2) | `python scripts/run_graph.py --compare` |
| 2. Supervisor по-настоящему | `team/supervisor.py` — AutoGen `SelectorGroupChat`, цена выбора | `python scripts/run_supervisor.py --mode all --critic tests` |
| 3. Капстоун | `team/triage.py` — триаж тикетов, судья-код, команда vs одиночка | `python scripts/run_triage.py` (+ `TEAM_BACKEND=proxy`) |

```
agent-team/
├── team/
│   ├── config.py       ← Settings из env: OLLAMA_URL, TEAM_MODEL, TEAM_THINK, TEAM_BACKEND, …
│   ├── llm.py          ← OllamaChat (/api/chat, think полем запроса), ProxyChat (ollama-proxy), ScriptedLLM (тесты)
│   ├── log.py          ← Message / TeamLog из 7.2 + shape() для сравнения журналов
│   ├── judge.py        ← тесты в subprocess с таймаутом, читаемый отчёт, TestJudge
│   ├── prompts.py      ← роли и промпты 7.2 — ОДИН источник для оркестратора и графа
│   ├── tasks.py        ← normalize_phone и parse_size с приёмочными тестами
│   ├── imperative.py   ← run_team из урока 7.2 (эталон поведения)
│   ├── graph.py        ← задание 1
│   ├── supervisor.py   ← задание 2
│   └── triage.py       ← задание 3
├── scripts/            ← run_graph.py, run_supervisor.py, run_triage.py
├── tests/              ← 56 тестов без сети (ScriptedLLM); без AutoGen один помечается skip
├── runs/               ← журналы живых прогонов, на которые ссылается этот README
└── requirements.txt
```

## Установка

```powershell
cd 07-multi-agent\agent-team
pip install -r requirements.txt                     # httpx, pydantic, langgraph, pytest
pip install "autogen-agentchat==0.7.5" "autogen-ext[ollama]==0.7.5"   # только для задания 2
pip install "protobuf>=6.33"                        # вернуть: autogen откатывает protobuf до 5.29
pytest                                              # 55 passed + 1 skipped без AutoGen; Ollama не нужна
```

Модель по умолчанию — `qwen2.5:3b`, как во всём модуле. Другая — через
`TEAM_MODEL`; для thinking-моделей (`qwen3.5`) держите `TEAM_THINK=0`, иначе
рассуждения съедят `num_predict` и агенты будут «молчать» (ловушка урока 5.2).

## Задание 1. Полный автомат на LangGraph

В уроке 7.4 на граф переехали два узла и лимит попыток. Здесь — весь автомат 7.2:

```
START → analyst → developer → tester ─┬─ accept ──→ finish → END
                    ▲                 ├─ retry ───→ tracer → fixer ─┐
                    │                 ├─ escalate → escalate ───────┤
                    └── (нет кода) ───┴─ give_up ─→ finish          │
                                      ▲─────────────────────────────┘
```

Решения, которых нет в формулировке задания:

- **Один текст промптов для обоих оркестраторов** (`team/prompts.py`). Иначе
  «сравнить журнал с 7.2» превращается в сравнение вкусов. Императивный
  `run_team` перенесён сюда без изменений логики — только LLM и судья приходят снаружи.
- **Три узла на одну роль разработчика** — `developer`, `fixer`, `escalate`. В 7.2 это
  один агент с тремя видами промптов; в графе отдельные узлы делают маршрут
  читаемым на картинке и в `state["nodes"]`.
- **Флаг `escalated` + счётчик `fix_rounds` в состоянии**, `route()` — чистая функция:
  `accept` / `retry` / `escalate` / `give_up` / `no_code`. Эскалация обнуляет счётчик —
  новый код заслуживает свой фикс-цикл, как в 7.2.
- **`tests/test_imperative_vs_graph.py`** — пять сценариев на ScriptedLLM (принято с
  первой попытки, после правки, после эскалации, «нужен человек», проза вместо кода):
  форма журнала, вердикт, код и **дословно каждый промпт** совпадают. Сценарий
  REJECTED стоит ровно 11 вызовов — как в живом прогоне урока 7.2.

Живой прогон (`runs/graph_normalize_phone.txt`, qwen3.5:9b, think=false): граф и
императивный оркестратор дали одинаковый журнал `spec → code → test_report`,
ACCEPTED с первой попытки, 2 вызова, 725+500 токенов; первый вызов 50 с — это
холодная загрузка модели, повтор той же реплики в императивном прогоне занял 7 с.
На 3B из урока картина другая (фикс-циклы и эскалация) — маршрут по узлам печатает
скрипт, сценарии с провалами покрыты тестами.

## Задание 2. Supervisor по-настоящему

`SelectorGroupChat` из трёх исполнителей, следующего выбирает LLM. Как посчитать
цену выбора:

- **Отдельный клиент для selector'а** (`make_client`): `total_usage()` и записи
  каждого вызова — токены на решения «кто следующий» не смешиваются с работой.
  Переспросы (модель не назвала ровно одно имя, AutoGen спрашивает до 3 раз) видны
  как `selector_calls − turns`.
- **`expected_next()` — политика конвейера 7.2 как функция.** По ней считаем «не те»
  выборы. Она же подставляется как `selector_func` в режиме `policy`: тот же
  AutoGen, ноль токенов на выбор — оркестратор 7.2 в одежде фреймворка.
- **Стоп-слова без ловушки подстроки:** `ВЕРДИКТ_ПРИНЯТО` и `ВЕРДИКТ_ДОРАБОТКА` —
  ни одно не входит в другое (частая ошибка 1 урока 7.4). Стоп-кран
  `MaxMessageTermination` остаётся обязательным.
- **Критик-судья (`--critic tests`)** — `BaseChatAgent` без LLM: гоняет приёмочные
  тесты и отвечает отчётом плюс стоп-словом. Тезис урока «в чате некуда воткнуть
  судью-код» уточняется: можно — судьёй становится участник.

Живой прогон (`runs/supervisor_critic_tests.txt`, qwen3.5:9b, критик-судья):

| режим | ходов | вызовов selector | токенов selector | доля | не по конвейеру | приёмка |
|---|---|---|---|---|---|---|
| selector | 2 | 2 | 1173 | **65 %** | 1/2 | 6/6 |
| policy | 3 | 0 | 0 | 0 % | 0/3 | 6/6 |
| roundrobin | 3 | 0 | 0 | 0 % | 0/3 | 6/6 |

Supervisor-LLM сразу выбрал разработчика, пропустив аналитика (по политике — ошибка,
по факту — сработало: 9B и без спеки пишет верно). Сэкономил ~600 токенов
исполнителей, но сами два решения «кто следующий» стоили 1173 токена — **65 %
всего расхода**: история чата целиком кладётся в промпт selector'а на каждом ходу.
Это и есть цена supervisor-паттерна из 7.1 в цифрах. На 3B ожидайте ещё и
переспросы с ошибками имени — считайте их по своему прогону.

## Задание 3. Капстоун: команда против одиночки на триаже тикетов

Задача из практики поддержки «Пингвин.Хост» (тикет-крик урока 7.1): по тексту
тикета выдать JSON `{category, priority, facts[], needs_human, summary}`.

**Судья — код, три проверки, отчёт `[PASS]/[FAIL]` строками** (`TriageJudge`):

| проверка | что ловит |
|---|---|
| `schema` | JSON парсится и проходит pydantic-модель `Triage` (`extra="forbid"`, литералы, длины) |
| `grounded` | каждая цитата в `facts` есть в тикете (регистр, ё, кавычки, тире, пробелы не считаются) — выдуманный факт аналитика из 7.1 теперь ловится кодом |
| `rules` | консистентность полей по политике: R1 outage не бывает low/normal; R2 critical только outage/access; R3 high/critical без конкретики (домен, код, время, номер) — крик; R4 возврат денег → `needs_human`; R5 question → low/normal, без человека; R6 outage и любой high/critical → `needs_human`; R7 billing → low/normal |

**Eval — 12 тикетов с золотой разметкой** (все категории, все приоритеты, оба
значения `needs_human`), у каждого `gold_fact` — дословная цитата. Тест
`test_gold_labels_are_consistent_with_the_rules_judge` требует, чтобы золото
проходило собственного судью: иначе судья спорит с eval'ом, и фикс-цикл учит
модель ошибаться.

**Три конфигурации одним eval'ом:**

- `solo` — один вызов, судья только оценивает;
- `solo+fix` — одиночка + фикс-цикл по отчёту судьи (≤1 раунд), потом «нужен человек»;
- `team` — экстрактор цитат → **код отбрасывает незаземлённые** → триажёр → судья →
  фикс-цикл → «нужен человек».

Разница `solo` → `solo+fix` — польза судьи-кода; `solo+fix` → `team` — польза
разделения ролей. `paid_off()` печатает вердикт по цифрам: дельта качества
(среднее точностей category / priority / needs_human) против цены в токенах.

**Через `ollama-proxy` (урок 5.7):** `TEAM_BACKEND=proxy` переключает все вызовы
на `ProxyChat` — `/generate` с `X-API-Token`, честное ожидание `Retry-After` на
429, `degraded_to` из ответа считается в `degraded_calls`. Прокси добавляет то,
чего у команды нет: аутентификацию, лимит на токен, потолок `num_predict`,
метрики и запасную модель. В `ollama-proxy` для этого добавлена настройка
`PROXY_THINK` (по умолчанию `false`): thinking-модель за прокси иначе тратила бы
весь `num_predict` на рассуждения.

### Живой прогон (qwen3.5:9b, think=false, `runs/triage_all_modes.txt`)

| метрика | solo | solo+fix | team |
|---|---|---|---|
| принято судьёй / эскалаций | 92 % / 1 | 100 % / 0 | 100 % / 0 |
| схема · цитаты заземлены | 100 % · 100 % | 100 % · 100 % | 100 % · 100 % |
| category верно | 92 % | 92 % | 92 % |
| priority верно (точно / ±1) | 58 % / 100 % | 50 % / 100 % | **75 %** / 100 % |
| needs_human верно | 92 % | 83 % | 92 % |
| качество (среднее трёх) | 81 % | 75 % | **86 %** |
| вызовов LLM / токенов / секунд | 12 / 7881 / 29 | 13 / 8741 / 30 | 26 / 12052 / 41 |

`paid_off()`: «+11 п.п. качества за ×1.4 токенов против solo+fix». Читать это надо
трезво:

- **На 9B формат и заземление — 100 % у всех трёх.** Судья-код здесь ловит не
  формат, а политику: единственная эскалация одиночки — T02, `billing/high`
  (правило R7), и фикс-цикл её починил за один раунд.
- **Разница solo → solo+fix (−6 п.п.) — шум, а не эффект.** Промпт одиночки в обоих
  режимах один и тот же, фикс сработал один раз, но два тикета из двенадцати
  разошлись уже на первом вызове (T01 `critical`→`high`, T06 `bot`→`human`):
  при `temperature=0` Ollama на GPU не даёт побайтовой повторяемости. На 12 тикетах
  один тикет — это 8 п.п.; сравнивайте только разницы больше двух тикетов.
- **Выигрыш команды — приоритет:** 9/12 против 6–7/12 (T01 и T09 стали `critical`,
  T02 — `normal`). Правдоподобная причина — триажёр получает уже отобранные цитаты
  и меньше отвлекается на текст; но и это 2–3 тикета. Честный вывод: **на сильной
  модели команда окупается только точностью приоритета и стоит ×1.5 токенов**;
  окупится ли — зависит от цены ошибки в приоритете у вас. На 3B, где формат
  и заземление ломаются сами, картина будет другой — прогоните.
- **Первая версия политики (`runs/triage_policy_v1.txt`)** дала 100 % по судье и
  42 % по `needs_human` у всех режимов: правила не определяли, что значит «нужен
  человек», и eval мерил размытость ТЗ, а не команду. Вторая версия добавила
  определения категорий, семантику `needs_human` и правила R6–R7 — и тест
  «золото проходит судью» удержал разметку и правила согласованными.

**Через ollama-proxy** (`runs/triage_via_proxy.txt`; прокси с `PROXY_RATE_LIMIT_PER_MIN=6`,
`PROXY_THINK=0`): 4 тикета командой — 9 вызовов `/generate` OK, **2 ответа 429**,
`ProxyChat` подождал `Retry-After` и повторил (T03 занял 54 с вместо 3 — это и есть
лимит в действии), качество 92 %, деградаций 0, `proxy_gen_tokens_per_second_p50 45`.
Команда ничего не знает о лимитах, токенах и метриках — всё это дала обвязка урока 5.7.

**parse_size на графе** (`runs/graph_parse_size.txt`): задача, на которой 3B в уроке
7.2 сидела на 0/6 весь прогон, у 9B принята с первой попытки — 2 вызова, 711+985
токенов, 23 с. Сходимость фикс-цикла — свойство модели, а не оркестратора (7.4).

## Честные ограничения

- Живые числа сняты на `qwen3.5:9b` — единственной модели в Ollama на момент
  прогона. Уроки модуля живут на `qwen2.5:3b`, где фикс-циклы, эскалация и
  переспросы selector'а проявляются куда чаще; повторите скрипты на 3B и сравните.
- Правила R1–R5 — консистентность, а не классификатор: судья не решает задачу за
  модель, он ловит противоречия. Категорию/приоритет он не проверяет по золоту —
  это делает eval.
- 12 тикетов — размер урока, не прода. Разница в несколько тикетов между
  режимами — шум; смотрите на структурные метрики (заземление, схема, эскалации).
- Правило «отбросить незаземлённые цитаты между ролями» — оркестраторская
  валидация кодом (7.2), а не часть модели: она честно засчитывается команде как
  преимущество архитектуры.
