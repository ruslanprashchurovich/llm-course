# ADR-0005. Контракт API: строгие схемы и производные поля

Дата: 2026-09. Статус: принято.

## Контекст

Схемы v1 (`app/schemas.py`) были «формой»: перечень полей с границами
значений. Живые прогоны уроков 8.3–8.4 и разбор чужих RAG-сервисов показали
три класса тихих ошибок, которые такая форма пропускает:

1. **Опечатка в имени поля молча игнорируется.** `{"query": ..., "topk": 3}`
   возвращает пять результатов вместо трёх — и никто не узнаёт почему.
2. **Неявные приведения типов.** `"3"` становится 3, `"yes"` — True. Клиент
   не узнаёт, что прислал не то, пока не пришлёт `"no"` и не получит True.
3. **Факты, которые каждый клиент вычисляет сам по ответу** — какие номера
   [N] процитированы, не выдуман ли номер, отказ ли это — считаются
   по-разному в каждом клиенте. А 3B-модель пишет отказ с хвостом
   `[1]-[5]` (урок 8.4), и наивный клиент видит в нём обычный ответ.

## Решение

1. Все тела запросов наследуют `ApiRequest`: `extra="forbid"`, `strict=True`,
   `str_strip_whitespace=True`. Пустой запрос из пробелов — 422.
2. Правила на несколько полей — `model_validator` в схеме: `fetch_k >= top_k`;
   `fetch_k` только вместе с reranker'ом (иначе параметр молча игнорировался бы).
3. Ответы считают производные поля сами (`computed_field`): `count`,
   `ranked_by` у поиска; `cited`, `dangling_citations`, `is_refusal`
   у генерации; `failed` у readiness. Константа `REFUSAL_MARKER` общая для
   промпта и детектора отказа — разъехаться они не могут.
4. События SSE — модели с дискриминатором `event` (`SourcesEvent`,
   `TokenEvent`, `DoneEvent`, `ErrorEvent`) плюс `format_sse`/`parse_sse`.
   Формат на проводе не меняется: имя события в строке `event:`, поля — в `data:`.
5. Инварианты ответов — в схеме: `ReadyResponse.status == "ready"` тогда и
   только тогда, когда все чеки ok (собирается через `from_checks`);
   источники `GenerateResponse` пронумерованы 1..N в порядке промпта.
6. Единый `ErrorResponse {detail, request_id}` для 5xx/503/404 через
   обработчики исключений; 422 остаётся в стандартном формате FastAPI —
   его понимают все клиенты и генераторы SDK.
7. `created_at` истории — `datetime` в UTC (ISO 8601 с `Z`) вместо сырой
   строки SQLite без таймзоны.
8. Числа с плавающей точкой округляются на проводе до четырёх знаков
   (`field_serializer`): 0.8700000047683716 — шум float32, не данные.

## Альтернативы

- **Оставить lax-режим** («клиенту удобнее»). Удобство оборачивается
  отладкой «почему пять результатов, я просил три». Строгость дешевле
  на границе, чем догадки внутри.
- **Считать `cited`/`is_refusal` в роутере** и класть в обычные поля.
  Работает, но у ответа два места сборки (JSON и SSE), и логика
  разъезжается при первом рефакторинге; `computed_field` считается
  одинаково везде, где есть объект.
- **Дублировать `event` внутри `data`** — самоописывающиеся события для
  клиентов без именованных слушателей. Ломает формат, зафиксированный
  уроком 8.4 и тестом стрима; отказались.
- **Строгие ответы** (`strict` и на response-моделях). Ответы собираем мы
  сами из типизированных объектов — лишняя проверка без выигрыша.

## Последствия

- Строгий разбор — формально несовместимое изменение для клиентов,
  присылавших мусор. У внутреннего v1 таких клиентов нет, поэтому версия
  приложения не поднимается; в публичном API это была бы мажорная версия
  или префикс `/v2`.
- Ответы чуть больше (три-четыре поля), зато клиенты перестают дублировать
  логику, а UI может показывать «висячие» ссылки и отказы специальной заглушкой.
- Нарушение инварианта ответа — `ValidationError` при сборке и 500: это наш
  баг, и он должен быть громким, а не тихой подменой смысла у клиента.
- Формат `created_at` в `/api/history` сменился на ISO 8601 — в живом прогоне
  урока 8.4 ещё виден старый формат SQLite; клиенты парсят дату стандартно.
- Схемы стали слоем с собственными unit-тестами (`tests/unit/test_schemas.py`):
  контракт проверяется без HTTP и приложения.
