# Миграции базы данных

Как менять схему PostgreSQL, не роняя прод.

## Инструмент

Миграции пишутся на Alembic и живут рядом с кодом сервиса в `migrations/`.
Одна миграция — одно логическое изменение. Автогенерацию используем как
черновик: сгенерированный код обязательно вычитывается руками.

## Обратная совместимость

Главное правило: миграция обязана быть обратно-совместимой с предыдущей версией
кода, потому что при откате деплоя миграции НЕ откатываются. Практически это
значит: сначала добавляем новое (колонку, таблицу), деплоим код, который пишет
в оба места, и только в следующем релизе удаляем старое. Удаление колонки —
всегда отдельный MR минимум через один релиз после прекращения записи.

## Опасные операции

Запрещены без согласования с DBA: `ALTER TABLE` с перезаписью таблицы на
таблицах больше 10 млн строк, создание индекса без `CONCURRENTLY`, `NOT NULL`
без дефолта на существующей колонке. Долгие миграции оформляются как фоновые
backfill-задачи с батчами и паузами.

## Процесс

Миграции применяются автоматически на dev и staging и вручную на проде —
отдельным manual job `migrate-prod` ПЕРЕД `deploy-prod`. Прогон миграции
на копии прода входит в чек-лист staging для миграций тяжелее секунд.
