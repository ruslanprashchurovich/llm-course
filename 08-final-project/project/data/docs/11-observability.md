# Наблюдаемость: логи, метрики, алерты

Что сервис обязан отдавать о себе и как этим пользуются дежурные.

## Логи

Логи пишутся в stdout в формате JSON — их собирает промышленный агент и
складывает в Loki. Обязательные поля: `timestamp`, `level`, `service`,
`request_id`, `message`. Сквозной `request_id` приходит из заголовка
`X-Request-ID` и пробрасывается во все внутренние вызовы — по нему собирается
путь запроса через все сервисы. В логи запрещено писать персональные данные
и секреты; вопросы пользователей логируются длиной и хешем.

## Метрики

Каждый сервис отдаёт Prometheus-метрики на `/metrics`: счётчик запросов
с метками метода/пути/статуса, гистограммы латентности, ошибки внешних
зависимостей. Правило кардинальности: в метках не бывает user_id, id сущностей
и других неограниченных значений. Дашборды — в Grafana, по одному обзорному
на сервис: RPS, p50/p95/p99, ошибки, насыщение.

## Health-эндпоинты

У каждого сервиса два эндпоинта: `/health` (liveness — процесс жив; без
внешних проверок) и `/ready` (readiness — зависимости доступны; по нему
балансировщик решает, слать ли трафик). Путать их нельзя: внешняя проверка
в liveness приводит к каскадным рестартам здоровых процессов при падении
одной зависимости.

## Алерты

Алертим по симптомам, а не по причинам: рост p95, рост доли 5xx, очередь
растёт быстрее, чем разгребается. Каждый алерт обязан иметь runbook — ссылку
на инструкцию «что делать». Алерт без runbook'а не заводится.
