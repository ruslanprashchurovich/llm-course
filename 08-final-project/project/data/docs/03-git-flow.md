# Git-процесс

Как мы работаем с ветками, коммитами и merge request'ами.

## Ветки

Главная ветка — `main`, она всегда деплоится на dev автоматически. Рабочие ветки
называются `feature/<тикет>-<краткое-описание>`, например
`feature/VEC-1234-export-csv`. Ветки живут коротко: цель — влить MR за 1–2 дня.
Долгоживущие ветки развалятся на конфликтах — дробите задачу.

## Коммиты

Сообщения коммитов — в стиле Conventional Commits: `feat:`, `fix:`, `refactor:`,
`docs:`, `test:`, `chore:`. Первая строка — до 72 символов, в теле — «зачем»,
а не «что» (что видно из диффа). Squash при мерже включён по умолчанию, поэтому
внутри ветки коммитьте как удобно, но заголовок MR станет сообщением коммита
в main — пишите его по правилам.

## Merge request

MR обязан пройти два условия: зелёный CI и минимум один аппрув ревьюера (для
изменений в платёжном коде — два). Крупные изменения дробите на цепочку MR
по 200–400 строк: гигантские MR ревьюятся неделями и вливаются с конфликтами.
Черновик помечайте префиксом `Draft:` — CI по нему гоняется, но ревьюеров
не назначается.

## Запреты

Прямые пуши в `main` запрещены для всех, включая тимлидов. Force-push в общие
ветки запрещён. `git rebase` своей рабочей ветки — на ваше усмотрение до первого
ревью; после начала ревью — только merge, чтобы не ломать историю комментариев.
